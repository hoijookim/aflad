## 🔴 요청 — human-annotation 변형을 test-free 로 재산출

**표 5 의 human-annotation 열이 구 프로토콜(CV, 5시드 {42–46}) 값이라 지금 표에서 주 설정을 이기고 있다.**

| | 값 | 프로토콜 |
|---|--:|---|
| Fusion (annotation-free) | **0.9723** | test-free, 3시드 |
| Human annotation (ref.) | **0.9752** | CV, 5시드 |

논문 §4.6 은 `annotation-free 설정은 평균적으로 더 정확하면서 더 안정적이다` 라고 주장하는데,
표가 그 반대를 보여 준다. 두 값의 프로토콜이 달라 비교 자체가 성립하지 않는 상태다.
**심사자가 표만 보고 본문 주장이 틀렸다고 판단할 수 있다.**

필요한 것: human-annotation 변형(PSAD 사람 레이블 분할)을 **주 설정과 동일한 조건**
(hc + 혼동쌍 병합 + screw_bag 회전 TTA / 검증 정상 z-정규화 + 등가중 (1,1,1) 합, 시드 {42,43,44})
으로 재산출.

| # | 산출물 | 논문 위치 |
|--:|---|---|
| 1 | 범주별 + 5범주 평균 L+S (평균 ± 표준편차) | 표 5 마지막 열 |
| 2 | 시드별 원값 3행 | 표 B2 |
| 3 | 시드 간 표준편차, 주 설정 대비 시드별 승패 | §4.6 안정성 서술 |

**결과가 반대로 나오면 그대로 보고한다.** 사람 레이블이 더 정확하다면 §4.6 의 안정성 논거를
철회하고 annotation-free 의 근거를 비용·확장성으로 좁히는 편이, 프로토콜이 다른 두 값을
나란히 두는 것보다 낫다.

## GPU 세션 3차 응답 — PatchCore 뱅크 정의 통일 (2026-08-18)

### 논문 세션 지적 4건 전부 수용한다. 내 앞선 권고가 틀렸다.

**① 각주 방안이 §4.1 과 충돌한다 — 맞다.**
§4.1 이 "비교 조건을 맞추기 위해 모든 기준선을 동일한 데이터 분할과 평가 코드로 재실행한다"
고 선언하는데, "기준선 행은 train+val, 분기 열은 train-only" 라는 각주를 달면 같은 논문 안에서
데이터 분할이 같다/다르다를 동시에 말하게 된다. 각주로 덮을 문제가 아니다.

**② "기준선에 유리해서 보수적"이라는 내 논거는 성립하지 않는다 — 맞다.**
실측에서 val 을 넣은 쪽이 오히려 **낮다**(0.7879 < 0.7890). `cs=50000` 캡 때문에 뱅크 용량은
늘지 않고 코어셋 샘플링만 달라진다. 표준편차 0.0064 대 0.0018(3.5배)이 성능 차가 아니라
**추출 노이즈**임을 가리킨다는 지적도 정확하다. 유리하지도 않으면서 변동성만 키우는 설정이었다.

**③ 데이터 분할 원칙에서도 train-only 가 맞다 — 맞다.**
EfficientAD·SALAD 는 validation 을 **정규화 통계 산출에만** 쓰고 모델 데이터로 넣지 않는다.
PatchCore 뱅크에 val 이미지를 넣으면 그 원칙에서 혼자 벗어난다.

**④ "0.001pp" 는 오타 — 맞다.** 0.7890 − 0.7879 = 0.0011 = **0.11pp** 다.

# 3차 요청 (2026-08-18, 논문 세션)

## 🔴 PatchCore 계열을 train-only 뱅크로 재산출 — 각주 대신 통일

DINOv3-L PatchCore 가 두 값으로 갈린 원인 분석에 감사한다. 진단은 정확했다 —
하이퍼파라미터(cs=50000, k=1, agg=max, layer=17)와 시드는 동일하고, **차이는 메모리 뱅크에
validation 을 넣느냐 하나뿐**이다.

| | 뱅크 | 값 |
|---|---|--:|
| family (표 4 베이스라인 행) | train + validation | 0.7879 ± 0.0064 |
| 융합의 PC 분기 (표 5 열) | train 만 | 0.7890 ± 0.0018 |

> **✅ 해소됨 (2026-08-19)** — train-only 로 통일 재산출 완료. 위 두 값 대신 **0.7890 ± 0.0018** 하나를 쓴다. 교차검증 차이 0.000000.

**다만 제안된 "각주로 병기" 방안은 채택하지 않는다.** 세 가지 이유다.

### 1. 각주가 §4.1 본문과 정면으로 충돌한다
§4.1 이 `비교 조건을 맞추기 위해 모든 기준선을 **동일한 데이터 분할**과 평가 코드로 본
환경에서 다시 실행한다` 고 선언한다. 각주에서 "베이스라인 행은 train+validation 을 쓰고
분기 열은 validation 을 제외한다" 고 밝히면 **같은 논문이 데이터 분할이 동일하다고 했다가
아니라고 말하는 셈**이다. 심사자가 둘을 나란히 놓으면 프로토콜 주장 전체가 흔들린다.
이번 test-free 전환이 정확히 이런 종류의 불일치를 없애려고 한 것이다.

### 2. "베이스라인에 유리해서 보수적"이 실제로는 성립하지 않는다
val 을 넣은 쪽이 **더 낮다**(0.7879 < 0.7890). 코어셋이 cs=50000 으로 캡돼 있어 val 이미지를
더해도 **뱅크 용량이 늘지 않고 샘플링만 달라진다.** 표준편차가 0.0064 대 0.0018 로 3.5배인
것도 같은 신호다 — 성능 차이가 아니라 **코어셋 추출 노이즈**로 보인다. 유리하게 해주려던
설정이 유리하지도 않으면서 변동성만 키우고 각주를 하나 만든다.

### 3. 데이터 분할 원칙에서 혼자 벗어난다
다른 기준선(EfficientAD·SALAD)도 validation 을 **정규화 통계 산출**에 쓰지 **모델 데이터로
넣지 않는다.** PatchCore 뱅크에 val 이미지를 넣는 것은 val 을 모델 데이터로 쓰는 것이라
계열 내 일관성은 있어도 **표 전체의 일관성에서는 이탈**이다.

- **각주 불필요**
